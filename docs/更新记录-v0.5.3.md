# 浮光 FloatShot v0.5.3：完整模型显卡加速

保留 C++20 + Qt、完整 PP-OCRv6 medium 检测/识别和 PP-LCNet x1.0 方向模型。新增 DirectML 显卡推理、批量文字识别、按阶段显示进度，以及显卡失败时自动回退 CPU。识别完全在本机运行，无需服务器、Python 或 CUDA。

## 为什么整屏慢，减少语言是否有效

对 AMD Ryzen 5 9500F、AMD Radeon RX 580 2048SP（约 4 GB 显存）进行分阶段实测。2560×1440 图片包含 3 列、每列 40 行，共 120 行 16 px 中英数字混排文字。原 CPU 流程耗时 16.263 秒：模型加载 0.294 秒，解码 0.040 秒，检测 2.312 秒，方向分类 0.380 秒，文字识别 13.215 秒。主要瓶颈是逐行运行完整识别模型，模型加载只占很小部分。

50 种语言是同一个识别模型的覆盖范围，不是同时运行 50 个模型。减少下拉选项或删除字典字符不能缩小现有神经网络；字典索引必须和模型输出严格对应。只有换用不同结构或重新训练的模型，才可能改变计算量。

使用同一图片、同一完整检测器/方向分类器，另测 PP-OCRv5 server 和 mobile 识别模型，结果如下。此处是模型比较，不是“关闭几种语言”的严格单变量实验。

| 识别模型与设备 | 整张冷进程耗时 | 文字识别阶段 | 120 行样本字符错误 | 8 张中英样本字符错误 |
| --- | ---: | ---: | ---: | ---: |
| 当前完整 PP-OCRv6 medium / CPU（原流水线） | 16.263 秒 | 13.215 秒 | 0 / 4812 | 2 / 448 |
| 当前完整 PP-OCRv6 medium / 显卡批量 | 5.101 秒 | 3.437 秒 | 0 / 4812 | 2 / 448 |
| PP-OCRv5 server / 显卡批量 | 5.266 秒 | 3.402 秒 | 0 / 4812 | 0 / 448 |
| PP-OCRv5 mobile 识别器 / CPU | 7.800 秒 | 5.124 秒 | 本项未计分 | 本项未计分 |
| PP-OCRv5 mobile 识别器 / 显卡批量 | 4.086 秒 | 2.363 秒 | 20 / 4812 | 3 / 448 |

v5 主识别模型主要面向中简繁、英文、日文等常用文字，相比 v6 的 50 语种宣传范围更集中，但 server 识别权重约 80.7 MiB，比当前 v6 medium 的 73.1 MiB 还大，本次并未更快。mobile 识别权重约 15.9 MiB，提速伴随样本错误增加；实验中检测器与方向模型仍是完整档，不能把这行数字当作整套轻量 OCR 的成绩。

本版先保留完整模型，不把 mobile 实验权重加入发布包。只在这些合成样本上，v5 server 少两个错字，不代表在真实截图中整体优于 v6；要更换默认模型还需要真实样本验证。文字体系覆盖仍见 v0.5.2 更新说明。

以上是同机实测快照，含模型加载与解码，不是多次测量的平均值，也不是性能保证。完整模型 CPU/GPU 的 120 行输出逐字相同；与人工文本对照只忽略空白，保留大小写、标点和简繁差异。这些样本不能代表所有语言和截图的总体准确率。完整模型大图约提速 3.2 倍，**120 行仍需约 5 秒，没有达到微信式整屏秒出**。微信内部模型和加速路径没有可靠证据，不能据此推断其实现。

## 使用和实现

设置 → 文字识别 → 运算设备，或识别窗口内选择：

- 自动：宽高都至少 200 px、总像素至少 10 万的大图优先显卡；其他图片使用 CPU。
- CPU：强制本机 CPU。
- 显卡：强制显卡，不支持或运行失败时显示原因。

自动模式在显卡组件启动失败、运行出错或崩溃时重试 CPU。识别窗口显示加载、查找文字、已识别行数和耗时；完成后显示实际使用 CPU/显卡。最近的设备选择保存到设置。图片较大但文字很少时，自动模式不一定最快，可手动切换设备。

检测和文字识别在显卡运行；相近宽度的文字行分组，以 4 行一批识别，再恢复原阅读顺序，限制批次宽度以避免长行产生过多填充。方向分类留在 CPU，16 行一批。CPU 识别仍逐行：本机实验中 CPU 批量识别反而慢。所有发布模型保持原始精度，不量化、不删字典或缩小文字。DirectML 自动选择支持 DirectX 12 的硬件显卡，优先独立显存较大的设备，不要求 NVIDIA/CUDA。

## 内存和部署

GPU 路径在上述一次基准中，OCR 子进程峰值 Windows 工作集约 354 MiB。**这个数字不包含显存，不能和 CPU 工作集直接相加减来宣称总内存下降。** 模型仅在独立子进程中加载，识别完成或取消后退出；主程序仍不链接 ONNX Runtime/OpenCV/DirectML，也没有常驻模型来换取速度。

CPU ONNX Runtime 位于包根目录；GPU 运行库和独立识别程序在 `gpu/`，完整模型由两者共享 `ocr/`。不能用显卡版 DLL 覆盖根目录 CPU DLL。DirectML/ONNX Runtime 的版本、下载 SHA-256 和许可证记录在 `native/setup-ocr-sdk.ps1`、`native/THIRD_PARTY_NOTICES.md` 及 `licenses/`。

对照模型仅放在开发测试目录，发布包不包含 server/mobile 实验权重。原始实验报告在 `.test-artifacts/native-ocr-performance/`、`.test-artifacts/native-ocr-model-comparison/`；回归图片和报告在 `.test-artifacts/native-v0.5.3-ocr/`。包内包含 `comparison-report.json`、CPU/GPU 质量和密集文字耗时报告，便于复核。

## 验证和交付

原生回归 19 项、OCR 回归 11 项、录屏回归 10 项全部通过，没有跳过。OCR 包括相同图片的 CPU/GPU 结果对照、GPU 字符错误数、强制显卡与取消、真实运行库拒绝显卡后的自动 CPU 回退、组件缺失、中文路径、旋转和识别窗口关闭。GPU 检查每次重新执行，不复用历史结果文件。

清除开发 SDK/Python 路径后，在独立验证目录使用 Windows Qt 平台运行 8 项便携 OCR 检查通过，包括 GPU 运行库加载、回退和取消清理。QtTest 仅复制到独立验证目录，不进入发布包。发布主程序另跑 3 次合成 OCR，验证通过，主程序未加载 ONNX Runtime，无残留识别子进程。这个合成验证中主程序工作集约从 25.3 MiB 到 30.0 MiB；没有显示工作台、恢复用户贴图或录屏，不是用户日常启动内存的固定值。

最终完整回归中，同一 120 行图片 CPU 约 15.1 秒、GPU 约 5.0 秒，输出逐字相同；与上表实验之间的差异体现测量波动。8 张样本 CPU/GPU 都是 2/448 字符错误，Windows OCR 对照是 49/448。区域、全屏、第二屏的实际录制视频解码检查均通过，控制条和边框对应像素未被录入；结果限于本机测试环境。

发布包不包含 Python、QtTest、PDB 或实验替代模型。完整模型 SHA-256 在打包时逐项核对。

目录 `dist/FloatShot-Native-0.5.3/`，主程序为 `FloatShotNative.exe`。请保留整个目录。更新时用旧版托盘菜单退出，以释放 F1/F3 等热键，再启动新版。旧版发布目录保留。
