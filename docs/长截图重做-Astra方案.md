# picut 长截图重做：Astra 方案

> 依据《长截图重做：最小需求》独立提出的技术建议。本文只讨论方案，未修改产品代码，未构建、运行或安装；性能与可靠性判断均需通过原型验证。

## 1. 建议的主线

采用**屏幕图像采集 + 纵向位置估计 + 连续内容拼接**。不依赖浏览器扩展、DOM、OCR 或目标应用提供滚动位置，因此可用同一条基础路径覆盖网页、文档、代码与聊天窗口。

关键设计是：**先判断当前画面位于已捕获内容的哪里，再决定是否增加图片。** 长图始终代表一段已经得到验证的连续内容；正在观察的新画面可以暂缓接纳，不能因为用户向下滚动就直接追加。

这条路线可能更稳，主要不是因为某个匹配算法更强，而是它把三件事分开了：采集到画面、确认画面的位置、把像素写入结果。瞬时动画、匹配歧义和采集缺口由前两步处理，已经正确拼出的部分不会随每一帧重新改写。

首版追求正常手动滚动流畅可靠、往返查看不重不漏、快速滚动尽可能接住且失联可恢复。屏幕从未呈现给采集器的内容无法还原，完全相同的重复页面也未必能够唯一定位；这些情况必须可见地暂停扩展。

## 2. 从采集到成图

### 采集：优先保住有用的中间画面

建议以 **DXGI Desktop Duplication** 作为首选原型后端，按显示器取得桌面画面，再裁出用户选区。它符合 Windows 10 兼容范围，适合持续采集桌面；是否真正优于当前环境中的其他采集方式，由原型测量决定。显示器更新信息可用于减少无效处理，但不能当作网页滚动距离。

选区、输入图像与输出图片统一使用实际像素坐标，界面再换算为 Qt 坐标。第一版先支持单个显示器内的选区；跨显示器、捕获中移动窗口或改变缩放比例不作为连续拼接场景。锁屏、显示配置切换、采集失效时保留结果并暂停，恢复采集后重新验证位置。

采集不能等待预览绘制或完整拼接计算。保留一个有界的短时画面缓冲，让正常滚动时出现过的重叠内容仍有机会参与定位。重复静止帧可以合并；不能在计算变慢时无条件只留下最新帧，因为被丢掉的中间帧可能是跨越两屏的唯一联系。缓冲耗尽仍无法维持连续性时，应报告跟不上并请求回滚，而不是无限占用内存。

自己的边框、预览和按钮必须避开捕获内容；在兼容范围内验证捕获排除能力后，可把它作为补充手段。尤其不能假设所有 Windows 10 版本都能可靠排除覆盖窗口。其他应用遮挡、弹窗与受保护画面也应视为采集异常，不能拼进正文。

GDI 可作为兼容性备选，但需单独验证其图像正确性和实际采样能力；不在首版同时铺开多个后端。若 DXGI 原型收益不足，可以调整后端，后面的定位与拼接模型保持独立。

### 定位：验证一个纵向位移，而不是寻找一个最像的地方

第一版只建立纵向平移模型，不做页面透视校正、弹性变形或横向拼接。用图像的边缘、纹理等信息提出候选位移，再用分散在正文不同位置的区域验证是否支持同一位移。可从多尺度图像相关与分块一致性开始，暂不引入复杂学习模型。

定位需要同时回答：

- 是否确有一批属于滚动正文的区域在共同移动，而不是固定工具栏占据了相似度？
- 这个位移是否有足够、分布合理的重叠证据？是否还有另一个几乎同样可信的位置？
- 它与近期运动、已经确认的位置和原始画面是否一致？

不能仅凭总相似度高就通过。代码中的重复行、聊天里的重复消息、网格与大段空白会产生多个可信候选；鼠标滚轮方向只能帮助排序，不能替代像素证据，也不能换算成确定距离。证据不足时先保留待确认画面，利用随后的画面消除歧义；仍不能确定则暂停扩展。

相邻画面用于跟踪，已确认内容中的关键画面用于重新定位与校验，避免只累加相邻帧位移而让误差持续积累。关键画面匹配也必须验证唯一性；“在长图中搜到了相似画面”并不自动意味着位置正确。

### 成图：只扩展已经连通的内容

初始画面定义一个文档坐标区间；后续定位成功的视口也映射到同一坐标系。进入已有区间就是查看旧内容，超出上端或下端且重叠关系成立才增加新内容。因此从页面中间开始、先向下后向上都不需要另一套拼接逻辑。

每次增加图片前，确认它与已捕获区间连续。已经定位到远处但中间缺失的画面不能直接接在结果末尾；可以短暂保留用于恢复，但不计入可导出的完整长图。通过回滚重新连上已有内容后，再沿连续路径补齐。

画布保留原始像素及其来源，按块存储。接缝优先落在两幅画面都一致的区域；文字采用明确的像素切分，不用透明混合掩盖误差，避免重影。明显找不到可信接缝时，应继续等待或暂停，不能靠视觉修补宣布拼接成功。

已确认内容在本次会话中保持冻结。回看旧位置用于定位，不触发整片内容替换。由此生成的是用户滚动过程中采到的连续记录，不是整篇文档在同一个时刻的快照；这也是首版对动态页面必须说明的边界。

## 3. 真实页面的首版取舍

| 情况 | 首版处理 |
| --- | --- |
| 普通网页、静态文档、代码、聊天历史 | 主支持对象，优先保证正文清晰、连续、原始比例不变。 |
| 快速滚动 | 尽量通过中间画面维持联系；超过采集与定位能力时暂停扩展，提示向回滚动到已捕获区域。暂停后仍可结束并导出正确部分。 |
| 往返查看 | 在同一内容坐标中重新定位；已有内容不重复追加，必要时向上、向下扩展。无法唯一定位时不猜测。 |
| 固定侧栏、顶部栏、底部输入框 | 首版优先让用户选中真正滚动的正文。检测到固定区与正文运动冲突时，提示调整有效捕获区域，并明确展示最终范围。自动重排侧栏、保留一次页头页尾留到后续。 |
| 少量闪烁光标、表情或局部动画 | 可从定位证据中排除局部变化，用其他稳定区域确认位移。尽量绕开变化区域选择接缝；无法得到完整、可信的局部画面时暂停或提示避开该区域。不能保证动画处于同一时刻。 |
| 多个独立滚动面板、大面积视频、整页动画 | 首版要求缩小选区到一个稳定滚动区域；不能用一个纵向位移解释时停止扩展。 |
| 懒加载导致旧段落移位、聊天插入新内容、折叠展开、缩放或换页 | 重新验证内容坐标。若旧内容关系已经改变，提示页面变化，结束当前段或重新开始；首版不做持续文档版本合并。 |

固定区域需要同时解决“定位”和“输出”两个问题。仅仅忽略侧栏参与匹配，仍然把它连同每段正文一起追加，会在成图中反复出现。首版选择清楚的正文区域边界，是为了避免把这种结果误当成支持固定侧栏；任何缩小范围都必须让用户知晓，不能悄悄裁掉选中的内容。

局部动画也不是只加一个掩码就结束：掩码帮助定位，却无法保证导出的动画对象没有被截断。因此有限容忍应建立在接缝和像素来源可验证的前提下，大面积变化仍属于明确限制。

## 4. 预览与结束体验

预览以已确认长图为主，显示当前视口对应的位置。新内容确认后及时增长；有待确认画面时给出简短状态，避免让用户误以为“预览没变”等于没有工作。

默认把整张长图缩放到预览可用空间内，随长度变化自动适应屏幕；另提供当前接缝或局部原比例查看，避免长图越长，用户越无法辨认缺行与错位。预览尺寸不能反过来决定结果分辨率。

失败反馈应说明下一步，例如“滚动过快，向回滚动到已捕获内容后继续”“页面布局已变化，请结束当前截图或重新开始”。不要只显示匹配失败分数。用户随时可取消；结束时只提交已经确认的连续区间，明确提示是否存在尚未接上的画面。

原图分块、预览分级缩略，避免每新增一段就重新分配和缩放整张长图。会话要有内存、临时存储及输出大小边界，临近限制提前提示。对超长图，保存、复制、标注和贴图各自能承受的尺寸可能不同，必须实测；遇到限制仍保留已有结果，不把“成功捕获”变成结束时才丢失内容。

## 5. 与现有应用的衔接

工程入口显示现有应用采用 C++20、Qt 6.8 Widgets，可把新能力作为独立会话接入：由框选工具栏传入区域与初始图像，在会话中管理采集、内容位置、预览和结束动作，完成时通过现有截图结果入口进入复制、保存、标注或贴图流程。

会话对外应提供结果尺寸、已确认范围、状态及最终图像；内部采集后端与定位策略可替换。不要求兼容旧长截图算法，也不需要为了本次重做先改造整个截图编辑系统。原型阶段只需确认结果入口接受何种图像、超长尺寸如何流转，以及取消与失败时资源如何释放，再决定具体接口。

预览更新、位置计算和原始数据存储应能独立推进，但线程数量、队列长度、采样频率及判断阈值由测量确定，不提前写成需求。

## 6. 三个优先原型

### A. 先证明“正确接入”和“拒绝错误”可以同时做到

搭建带已知内容坐标的测试页面与文档，包含真实文本、相似段落、重复代码、大块空白、图片及小动画。录下正常滚动、快速滚动、急停和往返的图像序列，离线重复回放；额外人为移除中间画面，制造确实存在的缺口。使用正文像素与坐标真值核对结果，测试标记不能成为算法独有的定位捷径。

同时记录静态正常滚动的接纳率、漏行/重行/错位、错误接纳与暂停次数，以及回滚恢复是否成功。要证明正常场景足够好用，并且缺口和歧义不会静默进入结果；不能靠拒绝大多数画面获得漂亮的正确率。接缝逐段检查，导出整图也要与连续原文核对。

**推进条件：** 常见静态内容可顺畅拼接，往返不改变已确认像素，故意断开的序列能够暂停并恢复。若这一关做不到，先收紧支持场景或调整定位方法，不急着加入自动滚动。

### B. 验证桌面上实际采到的内容足以支撑定位

用选定后端覆盖项目最低 Windows 版本与常见 Windows 11 环境，在浏览器、文档、编辑器和聊天窗口中测试不同显示缩放、快速滚动、短时算力压力、覆盖窗口及采集重启。关注实际图像间是否仍有可用重叠、是否出现撕裂或自身界面入镜、采集到可见预览的延迟和资源占用。

**推进条件：** 常见设备上正常滚动不因自身处理阻塞丢掉关键联系，异常可识别且反馈及时；若不成立，先调整采集与缓冲设计，再考虑更复杂的匹配算法。

### C. 验证长时间使用与最终结果交付

用长文档持续捕获，并穿插回看、停止、恢复、取消与结束。检查长图增长后预览是否仍响应、内存与临时存储是否受控，以及保存、剪贴板、标注和贴图是否能正确接收同一结果。加入存储不足和导出失败，确认已捕获内容仍可保留或换一种方式交付。

**推进条件：** 预览成本不会随长图无约束增长，所有结束路径的图片范围一致，输出限制在失败前可解释。不要只验证一张短网页能保存。

## 7. 决策与待验证点

建议先交付“静态正文 + 双向位置管理 + 缺口恢复 + 实时预览 + 现有结果流程”，再评估固定页面装饰的自动处理、较强动态内容支持和自动滚动。

最大的不确定性有三项：重复或稀疏内容在实际应用中出现歧义的频率；最低支持环境能否持续提供足够重叠画面；现有编辑与剪贴板链路对超长原图的承受能力。以上原型正好分别验证它们。通过有限测试不能证明任意页面都可靠，发布范围应依据成功与失败样本共同确定，并把无法唯一判断时保留正确内容的行为作为产品能力的一部分。
